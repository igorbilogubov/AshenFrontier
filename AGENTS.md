# Работа над Ashen Frontier

## Начало задачи

Прочитай [STATUS.md](STATUS.md), [GAME.md](GAME.md) и [WORKFLOW.md](WORKFLOW.md). Для продуктовых изменений используй [GAME_DESIGN.md](GAME_DESIGN.md), для графики — [ART_DIRECTION.md](ART_DIRECTION.md) и README соответствующего ассета. Статус реализации описан в STATUS/GAME; дизайн-документ содержит также будущие гипотезы.

Единственная рабочая папка на этом Mac — `/Users/igorbelogubov/Projects/AshenFrontier`, текущая ветка `main`. По запросу пользователя от 15 сентября все чаты работают здесь. Не создавай дополнительные clone/worktree и не переключай общую ветку без прямого запроса. Перед изменениями проверь `git status --short`, текущую ветку и `git worktree list`; сохраняй чужие незакоммиченные изменения. Параллельные задачи согласуют непересекающиеся файлы по [WORKFLOW.md](WORKFLOW.md).

Общий локальный игровой сервер запускается из этой папки: `PORT=4732 GAME_PREVIEW_ALIAS=0 npm start`, сохранения — `data/`. Сначала проверь `/health` и процесс сервера: повторно используй работающий сервер, не запускай второй процесс с теми же данными. Изолированные тесты и стресс-тест используют свободный порт и временные данные. Не останавливай сервер во время чужой проверки без координации.

## Согласованные ограничения

- Выбраны Three.js + TypeScript и браузер как основная версия; desktop планируется на том же веб-клиенте. Основной клиент, сервер и общие правила переведены на строгий TypeScript. Следуй [TECHNICAL_DIRECTION.md](TECHNICAL_DIRECTION.md). Проба Godot удалена из рабочей папки по запросу пользователя; не возвращай её код, сборки и инструменты без нового запроса. iOS/Android-сборки не запускать без нового запроса.
- Камера с фиксированным ракурсом; вращение разрешено в мастерских моделей, в игре только зум и следование за героем.
- Движение только при удержании ЛКМ в сторону текущего курсора; отпускание прекращает движение/преследование. Не возвращать движение с WASD/стрелок, маршрут по клику/миникарте и пассивный поворот за мышью без нового запроса. Клавиши навыков и Shift для шага/бега остаются.
- Три класса: воин, лучник, маг. Класс выбирается только при создании героя и больше не меняется; существующие герои сохраняют текущий класс. Ровно шесть слотов снаряжения: оружие, доспех, шлем, сапоги, кольцо, амулет.
- Нижний HUD: круглая красная колба HP слева от центральных кнопок, синяя колба маны справа; уровень жидкости и текущий/максимальный запас отражают серверное состояние.
- В MVP экипировка даёт обычные характеристики, включая скорость атаки/каста; модификации отдельных навыков и особые боевые срабатывания на вещах отложены по запросу пользователя. Целевой режим — 2–3 активных часа в день плюс AFK, примерно три месяца развития. Конкретные 100 уровней, количество карт/вещей и предел +30% пока являются предложением в [MVP_90_DAYS.md](MVP_90_DAYS.md), не готовыми или окончательно утверждёнными правилами.
- Платежи отложены до выбора пользователем провайдера. AFK, PvP/PK и рынок пока описаны в плане, а не реализованы.
- Сервер определяет движение, бой и награды. Общие величины карты, дальности и тайминги согласовывать с клиентом; не переносить доверие к деньгам/урону на клиент.
- Существующие герои и остальные сайты на Hetzner должны сохраняться при изменениях.

## Код, ассеты и данные

Игровой код — строгий TypeScript, ES modules; сборка `npm run build` в `dist/`. Скрипты и тесты остаются JavaScript. Node.js 24, `ws`, Three.js; тесты — `node:test`. `npm ci` восстанавливает зависимости из lock-файла. Поставляемый клиент использует `public/game/vendor/`, поэтому изменение версии npm-пакета Three.js само по себе не обновляет браузерную библиотеку.

`data/`, `artifacts/`, резервные копии, `.env*`, ключи и содержимое `heroes*.json` не коммитить и не выводить. Даже приватный репозиторий не является хранилищем секретов. Тесты используют временных героев; онлайн-проверка создаёт реальные записи и выполняется только когда это входит в задачу.

Основные модели, GLB, исходные FBX, Blender-сцены, генераторы и отчёты сборки входят в репозиторий. Логи и автоматические `.blend1`-копии исключены. Перед генерацией читай README ассета: генератор перезаписывает `.blend`, `.glb`, рендер и отчёт. Проверяй именно экспортированный GLB в браузере. `art/creatures/wolf-v1-reference/` — неизменяемая контрольная версия для сравнения. Правила происхождения ассетов — [ASSETS.md](ASSETS.md).

## Проверки и передача результата

Фиксируй завершённые логические изменения отдельными локальными коммитами. Push выполняется только после отдельной команды пользователя; подготовка коммита или проверка не разрешает публикацию. Это правило действует и для работы в нескольких чатах. Пока push не разрешён, оставляй готовые коммиты в ветке и сообщай её имя.

Запускай `npm run check` и `npm test` после изменений кода. Для FPS используй изолированный `npm run stress`, методику и ограничения из [PERFORMANCE.md](PERFORMANCE.md); обычные сохранения и production для нагрузки не использовать. Для изменений вида/анимаций нужна также проверка в браузере; для серверных изменений — соответствующие проверки сети, миграций и сохранений. Успешные тесты не означают успешную выкладку.

В описании PR укажи результат, затронутые общие файлы/контракты, проверки и ограничения. В общей папке коммить только файлы своей задачи; общий контракт изменяется последовательно. PR подготавливается, когда это входит в запрос. Не выполняй force push в `main`. Бинарные модели не объединяются текстовым merge: согласуй одну версию исходника и пересобери экспорт.

В том же логическом изменении обновляй затронутые документы: STATUS/GAME для поведения, QA для доказательств, дизайн для принятого продуктового решения, ASSETS/README модели для графики. Поддерживай различие между готовым кодом, планом и опубликованным релизом. Исторические записи с датами не переписывай как новые результаты.

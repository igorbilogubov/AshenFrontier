## Зачем TypeScript

Типизация нужна для согласованных контрактов персонажа, предметов, статов и сетевых пакетов, безопасного изменения кода и параллельной разработки. Типы удаляются при компиляции и сами по себе не ускоряют выполнение: [документация TypeScript](https://www.typescriptlang.org/docs/handbook/2/basic-types.html#erased-types).

Исторический порядок перехода был таким: сборка и проверка типов → общие типы протокола/предметов/героя → небольшие модули правил и движения → сеть и клиентские системы. Этот перенос завершён. Статические типы не заменяют проверку входящих сетевых пакетов во время исполнения; текущие правила земли/магазина и экономический барьер остаются серверными.

## Как добиваться ровного FPS

Цель — стабильный кадр на определённых устройствах и настройках. Для 60 FPS доступно около 16.7 мс на кадр. Обещание отсутствия любых просадок на всех компьютерах невозможно проверить; минимальные системные требования и профили качества ещё предстоит определить.

Сначала нужен воспроизводимый профиль: одна активная игровая вкладка, без параллельных графических прогонов, фиксированные устройство/браузер, окно, DPR, камера, число сущностей и настройки графики. Сравнивать лагерь, движение по лесу и бой с эффектами. Отдельно измерять первый запуск/прогрев и повторный проход. Замеры повторить на Windows с интегрированной графикой и текущем Mac, затем на 1/4/16 клиентах без смешивания нагрузки генератора и измеряемого клиента.

Фиксировать необрезанные интервалы `requestAnimationFrame`, p50/p95/p99, число пауз свыше 50/100 мс, работу JavaScript/DOM, память/сборку мусора, вызовы рисования и треугольники. Время вызова `renderer.render()` на CPU не равно длительности GPU-работы. Проверять профиль в [Chrome DevTools](https://developer.chrome.com/docs/devtools/performance/reference), а не делать вывод только по среднему FPS на панели. Серверные время тика, задержку снимков и сеть измерять отдельно от FPS клиента.

Чтение кода 15 сентября выявило следующие **кандидаты для измерения, не доказанные причины просадок** в прежней меньшей сцене. Базовый профиль ниже выполнялся для карты с четырьмя спотами и 41 мобом; для текущих пяти лесных спотов, 71 лесного моба и отдельного Стадиума нужно повторить профиль в одинаковом сценарии:

| Участок | Что уже есть | Что проверить |
| --- | --- | --- |
| `public/game/environment.ts` | InstancedMesh для деревьев, 230 камней, 2000 травинок, 260 папоротников и 650 листьев; объединение статичной геометрии | Вызовы рисования, прозрачность/перекрытие листвы, деление на видимые участки, детализация при отдалении |
| `public/game/scene.ts` | Тени 2048×2048, свет следует за героем, DPR ограничен 1.25 | Вклад теневого прохода, разрешения и сглаживания; сравнить контролируемое отключение каждого эффекта |
| `public/game/mobs.ts`, `character.ts`, `scene.ts` | Каждый моб и герой из сетевого списка обновляют анимации; у мешей выключен frustum culling; дублирующие скелеты частей одного героя объединены | Частоту визуальных обновлений вне кадра, корректные границы скелетных моделей; не возвращать обрезание лап/оружия |
| `pickMob()` в `scene.ts` | Сначала raycast по мешам, затем запасной тест bounding box; выбор запускается по обновлению удерживаемого указателя | Стоимость выбора по детальным скелетным моделям; проверить простые объёмы выбора без ухудшения попадания курсором |
| Эффекты и подписи в `scene.ts` | Создание материалов/DOM для попаданий, обновление подписей игроков каждый кадр; основной HUD уже ограничен 10 Гц | Паузы сборки мусора, повторное использование объектов, обновление текста только при изменении |
| Счётчик FPS в `scene.ts` | Среднее по 90 интервалам теперь сохраняет зависания ≥0.5 секунды; отдельный стенд хранит сырые интервалы и p95/p99 | Отдельные метрики должны сохранять длинные зависания, которые скрывает текущий индикатор |

Простейшие меры уже частично применены: совет «добавить instancing» сам по себе не является новым исправлением. Three.js описывает влияние числа Mesh и объединение геометрии в [руководстве по оптимизации](https://threejs.org/manual/en/optimize-lots-of-objects.html). Любое изменение подтвердить замером до/после в одинаковом сценарии и визуальной проверкой сохранности качества.

После профиля: исправить алгоритм или лишнюю работу → проверить снижение детализации/эффектов и профили качества → при необходимости вынести независимые CPU-расчёты в Worker. Динамическое разрешение вводить только при измеренной GPU-нагрузке, с ограничениями и плавным переключением; оно не лечит тяжёлую работу JavaScript.

## Когда действительно нужен Rust

В браузере Rust обычно подключается как WebAssembly-модуль. Подходящие будущие кандидаты — крупные пакетные геометрические расчёты, генерация данных мира, специализированная физика или другая измеренно тяжёлая численная работа. Вынос требует измерить передачу/копирование данных, загрузку модуля и полное время операции. Множество мелких вызовов между JS и Wasm не гарантирует выгоды. Rust на основном потоке также может блокировать кадр.

Для независимых вычислений сначала можно проверить Worker с обычным JavaScript/TypeScript. Worker разгружает основной поток, но имеет расходы на коммуникацию: [разбор web.dev](https://web.dev/articles/off-main-thread). Для тяжёлого Wasm-модуля есть [пример организации работы в Worker](https://web.dev/articles/webassembly-performance-patterns-for-web-apps).

Переписывание управляющего кода на Rust не сокращает автоматически количество отрисованных полигонов, теневых проходов и пикселей. При GPU-ограничении оптимизируем графическую нагрузку. В нашей игре AI и авторитетный бой находятся на сервере: их возможный перенос на Rust — отдельная задача вместимости сервера, он не даёт прямого прироста FPS браузера. Клиент никогда не определяет опыт, золото или попадания.

## Desktop

Оболочка позволяет использовать тот же игровой клиент и сервер. Помимо самой упаковки остаются установка, подпись, обновления, оконные режимы и проверка каждой ОС. Упаковка сама по себе не гарантирует прирост FPS. Выбор оболочки и выпуск desktop не входят в текущую фиксацию направления; мобильные сборки по-прежнему не запускать без нового запроса.

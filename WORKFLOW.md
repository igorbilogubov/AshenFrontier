# Параллельная разработка в разных чатах

Проверено 14 сентября 2026. Один чат ведёт одну ограниченную задачу в своей ветке и рабочей папке. GitHub: [igorbilogubov/AshenFrontier](https://github.com/igorbilogubov/AshenFrontier), приватный репозиторий, `main` — ветка интеграции.

## Начало

Новая задача читает [AGENTS.md](AGENTS.md), [STATUS.md](STATUS.md), [GAME.md](GAME.md), затем документы своего направления. Пользовательский запрос определяет объём работы. Историю других чатов читать для уточнений можно, но проверенные решения и ограничения должны находиться в репозитории.

Первый clone на другом компьютере:

```sh
git clone https://github.com/igorbilogubov/AshenFrontier.git
cd AshenFrontier
npm ci
```

Нужен доступ к приватному репозиторию и Node.js 24 (`.nvmrc`). Git LFS для текущих файлов не требуется. Исходные Blender/FBX и runtime-ассеты уже входят в clone; локальные герои и секреты в него не входят. Blender нужен только для изменения моделей, не для запуска игры и тестов.

## Отдельная папка для задачи

Если чат уже запущен в собственном worktree, используй его. При ручном создании, из основной папки:

```sh
git status --short
git worktree list
git fetch origin
git worktree add ../AshenFrontier-manual-stats -b codex/manual-stats origin/main
cd ../AshenFrontier-manual-stats
npm ci
PORT=4732 GAME_PREVIEW_ALIAS=0 npm start
```

Имя `manual-stats` и порт 4732 — пример; другая задача получает другое имя и свободный порт, например 4733. Проверить порт на macOS: `lsof -nP -iTCP:4732 -sTCP:LISTEN`. Основной сервер на 4731 и редирект 4740 принадлежат основной папке; соседние задачи их не занимают.

По умолчанию сервер создаёт `data/` в своём worktree. Указывая `GAME_DATA_DIR`, выбирай отдельную папку только этой задачи. Два процесса не должны писать один `heroes.json`. Герои, созданные на разных портах/серверах, независимы. `.env` автоматически не загружается: переменные передаются окружением команды.

## Границы задач

В начале зафиксируй в своей задаче/PR цель, ветку, порт, основные файлы и контракт изменения. Учитывай, что `world.ts`, `public/rules.ts`, `location.ts`, `network.ts`, `scene.ts` и `interface.ts` часто нужны нескольким направлениям. Сначала объединяется PR с общим контрактом, затем зависимые ветки обновляются от `origin/main`.

Можно одновременно делать графику, измерять производительность и дорабатывать развитие, когда они не переписывают один модуль. Две системы наград, AFK и PvP не должны независимо изобретать разные версии сохранений. Один `.blend`/`.glb` изменяет одна задача; Git не объединит два бинарных варианта. Генерация выполняется в worktree владельца ассета и включает исходник, GLB, отчёт и визуальную проверку.

## Проверка и PR

```sh
npm run check
npm test
git diff --check
git status --short
git add <конкретные-файлы-задачи>
git commit -m "Describe the completed change"
```

Завершённые изменения коммитятся локально по логическим частям. **Push — только по отдельной команде пользователя.** Когда публикация разрешена:

```sh
git push -u origin HEAD
gh pr create --base main
```

Перед commit проверь список файлов: `data/`, `artifacts/`, ключи, локальные бэкапы и логи не должны попадать в Git. PR содержит результат, изменения протокола/данных, нужные проверки и ограничения. Обнови связанные Markdown-файлы в том же PR. Запуск новой функции в локальном браузере не является deployment.

GitHub Actions выполняет синтаксическую проверку и тесты на Node 24 для PR и push в `main`; это не проверяет графику глазами и не заменяет испытание нагрузки. Автоматической выкладки на Hetzner нет.

## Объединение

PR объединяются последовательно. Если `main` изменилась:

```sh
git fetch origin
git merge origin/main
# Разрешить конфликты по смыслу, затем снова выполнить проверки.
npm run check
npm test
# Push — после отдельной команды пользователя.
```

После проверки и разрешённого merge следующие задачи стартуют от нового `origin/main`. Для интеграции в основную папку с чистым `main`: `git pull --ff-only`. Обновление рабочей папки не перезапускает сервер; запущенный Node держит старые серверные модули, а браузеру может понадобиться reload. Обновление основного локального сервера согласуется с выполняющимся тестом; production — по [DEPLOYMENT.md](DEPLOYMENT.md).

Перед удалением завершённого worktree убедись, что все нужные изменения закоммичены/отправлены, сервер этой задачи остановлен, а локальные данные больше не нужны. `git worktree remove` удаляет и его игнорируемые файлы при принудительной очистке; не используй `--force` для обхода чужой незавершённой работы.

## Сообщение для нового чата

> Прочитай AGENTS.md, STATUS.md и WORKFLOW.md. Задача: [конкретный результат]. Работай в отдельном worktree и ветке от origin/main, выбери свободный порт и собственные тестовые данные. Проверь результат, обнови соответствующие документы и подготовь PR. Production не обновляй в рамках этой задачи.

Для намеренного продолжения конкретной незавершённой ветки укажи её вместо `origin/main` и используй существующий worktree. Так контекст следует за кодом, а новые чаты не делят одну изменяемую папку.

# Хранение аккаунтов и персонажей

Локальная реализация 16 сентября 2026; это не отчёт о deployment.

PostgreSQL schema 5 добавляет `accounts` и `account_sessions`. Уникальная идентичность Google — `google_sub`, а не email: изменение адреса не меняет аккаунт, одинаковый email разных subject не объединяет их. `Account` содержит id, email, name; сессии содержат только SHA-256 случайного cookie, аккаунт и срок действия. Проверка подписи Google и HTTP-cookie выполняется слоем авторизации до обращения к хранилищу.

`heroes.account_id` связывает героя с аккаунтом. До пяти персонажей на аккаунт: транзакция создания блокирует строку аккаунта, считает всех его героев и сохраняет героя вместе с предметами и журналом. Слоты 1–5, уникальный индекс и SQL-trigger дополнительно защищают лимит от прямой записи. Владельца и слот нельзя поменять после создания; класс по-прежнему неизменяемый.

Старый `heroes.token_hash` удаляется миграцией. Существующие гостевые герои остаются в базе с пустым владельцем и слотом; автоматического присвоения по старому ключу нет. `load(heroId,accountId)` и `listHeroes(accountId)` возвращают только героев указанного владельца. Переданный accountId должен происходить из проверенной серверной сессии. Нельзя изменять чужого или прежнего гостевого героя через `commit`.

Контракт `shared/accounts.ts`: `MAX_CHARACTERS=5`, `Account`, `CharacterSummary` (id, name, classId, level), `GoogleIdentity`. Методы хранилища:

- `upsertGoogleAccount(identity)` — существующий или новый аккаунт по Google subject.
- `load(heroId,accountId)` — герой с ревизией либо null; `listHeroes(accountId)` — список по постоянным слотам.
- `commit([{accountId,hero,expectedRevision}],operationId,reason)` — прежняя атомарная запись и идемпотентный журнал. Нулевая ревизия создаёт героя, шестой вызывает `CharacterLimitError`.
- `createSession(accountId,tokenHash,expiresAt:Date)`, `findSession(tokenHash)` (срок в миллисекундах Unix), `deleteSession(tokenHash)` — сохранение, проверка срока и отзыв сессии. Ограничение одного игрового подключения реализуется сервером игры, а не числом cookies в таблице.

Миграция требует остановленного прежнего world writer и выполняется под прежними advisory locks. База не заменяется, production-копии и отдельная сверка героев не выполнялись по действующему указанию пользователя.

Проверка в отдельной временной PostgreSQL: 8/8 storage-тестов. Покрыты идентичность Google, владение, двенадцать конкурентных созданий (успешны ровно пять), откат пакета из шести, прямой SQL сверх лимита, срок/отзыв сессии, миграция schema 4 → 5, инвентарь/броски, журнал и потеря writer lock. TypeScript самого хранилища проходит; общая проверка до интеграции закономерно показывает прежние вызовы token API в server.ts. Для выполнения изолированных тестов выполнена временная компиляция с `--noEmitOnError false`, конфигурация сборки не изменялась. Координатор выполняет полную проверку после объединения серверного и клиентского контракта.

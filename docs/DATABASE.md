## Запуск на Mac

Нужны Node.js 24, `npm ci` и бинарники PostgreSQL (`pg_ctl`, `initdb`, `pg_dump`). На рабочем Mac установлен PostgreSQL 14.20. Скрипты находят бинарники в обычных Homebrew-путях или через `PG_BIN`, если задана папка `bin`. Сначала проверить `/health`, PID и каталог работающего сервера 4732: второй процесс для тех же данных не запускать.

После согласованного перезапуска из основной папки:

```sh
npm run db:start
PORT=4732 GAME_PREVIEW_ALIAS=0 npm start
```

`npm start` сам создаёт или повторно использует локальный кластер, поэтому отдельный `db:start` удобен для проверки, но не обязателен. Без `DATABASE_URL` используется `data/postgres-local/` на `127.0.0.1:5473` (порт меняет `GAME_PG_PORT` до первого создания кластера). Закрытые параметры соединения и данные лежат там же и не входят в Git. `npm run db:stop` останавливает только помеченный локальный кластер; делать это при работающем игровом сервере нельзя. Если база уже создана с другим портом, скрипт не меняет её конфигурацию незаметно.

`DATABASE_URL` обязателен для production и изолированных серверов с `GAME_DATA_DIR`/стресс-режимом. Не печатать строку подключения, ключи героев, содержимое дампов и старых JSON. Локальный `.server.lock` защищает каталог от второго процесса, а PostgreSQL advisory lock удерживает единственного писателя общего мира. `GET /health` отдаёт `storage.backend='postgresql'`, `schemaVersion`, `writer` и `pending`; при недоступной базе/потере writer возвращает 503. Проверка успешного старта не доказывает восстановление из аварийного дампа.

## Что хранится

Схема версии 1 встроена в `storage/schema.ts` и применяется транзакционно при открытии хранилища. Таблица `heroes` содержит гостевой SHA-256-хеш ключа, класс, XP/золото, характеристики, позицию/ресурсы, квест и ревизию записи. `item_identity` удерживает глобальную идентичность экземпляра; `item_instances` хранит владельца и основу предмета; `item_rolls` хранит значения, исходные диапазоны и порядок статов. Запечатанные экземпляры и броски защищены триггерами от изменения. `inventory_locations` разделяет рюкзак (16 позиций), шесть слотов экипировки и сохранённую очередь прежних наград; один экземпляр не может одновременно быть в двух местах.

`operation_journal` хранит уникальный operation ID, хеш пакета и квитанцию ревизий. Обновление нескольких героев и связанных предметов проходит одной SQL-транзакцией; устаревшая ревизия или повтор ID с другим содержимым отклоняется. Сервер сравнивает экономические поля героя после каждого тика и подтверждает золото, XP, предметы, характеристики, квест и расход зелий **до** отправки следующего сетевого состояния. Движение/AI/бой остаются в памяти 20 Гц; неэкономическое состояние получает контрольные записи примерно каждые две секунды, при отключении и штатном завершении. Пока запись ожидает или повторяется после временного отказа, мир не продолжает тикать и не показывает неподтверждённую награду. Потеря writer-блокировки закрывает соединения и требует проверки состояния перед новым запуском.

Наземные личные стопки золота и вещи — временные объекты мира, а не строки PostgreSQL. Подобранное золото и экземпляр становятся постоянным состоянием героя; неподобранные объекты истекают через 180 секунд, ограничены 48 на героя и исчезают при рестарте. Состояние онлайн-AFK также не сохраняется. [Правила добычи и магазина](LOOT_VENDOR.md).

## Резервная копия и production

`npm run db:backup` создаёт новый custom-format дамп PostgreSQL в исключённом из Git `backups/`; `node scripts/database-backup.mjs /absolute/path/to/new.dump` задаёт путь явно и не перезаписывает существующий файл. Скрипт использует `pg_dump`, подключается через `DATABASE_URL` либо закрытую локальную конфигурацию и ставит права 0600. Само создание дампа не подтверждает восстановление: перед production-переходом проверить восстановление в отдельную тестовую БД и сравнить героев/вещи/ревизии.

До deployment `20260915-pg-01` была подготовлена следующая схема (теперь развёрнута по процедуре в DEPLOYMENT.md): `deploy/compose.yaml` для отдельного внутреннего сервиса `postgres:18.6-alpine` с постоянным volume, закрытой сетью, healthcheck и отдельными паролями администратора/игры. Он не заменяет опубликованный контейнер сам по себе. Переход на production требует отдельного релиза и обновлённого порядка из [DEPLOYMENT.md](../DEPLOYMENT.md): прежние шаги этого документа относятся к JSON-релизу и не являются готовой инструкцией PostgreSQL-перехода. Старый серверный JSON архивируется **без импорта** в новую БД, новая база проверяется, Caddy/остальные сайты сохраняются. После появления PostgreSQL-героев следующие релизы обязаны сохранять уже их данные и проверять совместимость схемы.

Архив исходного исследования и отклонённого плана импорта: [DATABASE_PLAN.md](DATABASE_PLAN.md).

## Локальная проверка перехода

15 сентября общий сервер 4732 перезапущен штатно и отвечает HTTP 200 с `storage.backend: postgresql`, `schemaVersion: 1`, `writer: true`, `pending: false`. Восемь прежних JSON-файлов скопированы в закрытый `backups/before-postgres-*`; их SHA-256 не изменился после запуска. Новая база пуста при переключении, герои не импортировались.

Custom-format резервная копия восстановлена через `pg_restore` в отдельную одноразовую базу PostgreSQL. У трёх тестовых героев совпали идентичность, характеристики, точные экземпляры/броски, экипировка, золото и ревизии. Сравнение выполнялось с фиксированным тестовым снимком, без конкурирующих изменений во время снятия дампа. Проверены права файла 0600. Это локальная проверка, не настройка внешнего backup-хранилища и не production-репетиция.

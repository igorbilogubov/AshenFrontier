# Хранилище Ashen Frontier: предложение PostgreSQL

15 сентября 2026. Рекомендация после вопроса пользователя о базе данных. Это план следующего этапа: PostgreSQL ещё не установлен и не подключён, JSON-сохранения остаются действующим хранилищем. Проверены текущие server.ts/world.ts, GAME/STATUS/WORKFLOW и официальная документация. Push/deployment не выполняются этой фиксацией.

## Почему сейчас

В server.ts сохраняется общий словарь героев: persistentHero → JSON.stringify → временный файл → fsync → rename. Запись сериализована, таймер — раз в 2 секунды, также есть сохранение при отключении и штатном завершении. Это лучше незащищённой перезаписи файла, но не даёт готовой транзакционной модели операций между героями, ограничений владения предметом и журнала экономики. Потеря изменений после последней успешной записи при аварии остаётся возможной; период таймера не гарантирует верхнюю границу потери при перегрузке/ошибке диска.

Для планируемого рынка, уникальных экземпляров со случайными статами, наград AFK и будущих покупок рекомендуем PostgreSQL. MySQL/InnoDB тоже технически подходит; менять игровой сервер или Three.js для этого не требуется. SQLite является полноценной транзакционной БД и подходит даже части серверных проектов, но для нашей цели общей экономики и нескольких серверных процессов разумнее сразу клиент-серверная БД. Redis пока не нужен; позднее может хранить восстанавливаемый кэш и рейтинги.

## Разделение работы

- Клиент передаёт команды игровому серверу. Прямого подключения браузера к БД нет.
- Движение, AI, траектории и активный бой остаются в памяти процесса World с обновлением 20 Гц. SQL-запрос на каждое движение или каждый кадр не добавляется.
- PostgreSQL хранит постоянный прогресс и подтверждённые операции экономики. Доступ асинхронный через отдельный слой хранилища; порядок операций героя и ревизии защищают от перезаписи свежих данных устаревшим снимком.
- Передача/продажа вещи, списание/начисление валюты, журнал операции и её уникальный ID фиксируются одной транзакцией. Успех экономической операции подтверждается клиенту после commit. Блокировки/условные обновления, ограничения БД и повторяемость команд проектируются явно: одна установка PostgreSQL сама по себе дюпы не исключает.
- Неэкономическое состояние сохраняется контрольными снимками; политика допустимой потери при аварии задаётся отдельно. Очередь записи ограничена, ошибка сохранения видна через health/метрики; недоступность БД не должна приводить к подтверждению неподтверждённых покупок/обменов.

## Первая схема

| Данные | Представление |
|---|---|
| Герои | id, неизменяемый класс, уровень/XP, вложенные статы, HP/MP/таймеры, последняя позиция и ревизия |
| Доступ | Привязка гостевой сессии к герою; хеш существующего секретного ключа вместо вывода/хранения его в журналах. Полноценная регистрация — отдельная задача |
| Предметы | Постоянный id экземпляра, владелец, definition/version, редкость, legacy power, привязка |
| Случайные свойства | Отдельные строки item_rolls с ключом, значением и исходным диапазоном; миграция не бросает статы заново |
| Расположение вещей | Рюкзак / один из шести слотов / очередь добычи; один экземпляр не может одновременно занимать две позиции |
| Прогресс | Квесты и полученные награды; версия правил и идентификатор выдачи при необходимости |
| Экономика | Баланс и журнал начислений/списаний с причиной и уникальным operation_id |

Каталог базовых предметов, формулы навыков и локации пока остаются версионируемым игровым кодом. Не превращаем первый этап миграции в редактор всего контента. JSONB допустим для небольших гибких дополнительных данных, если понадобится; весь мир или инвентарь одним JSON-документом не заменяют связи/ограничения таблиц. Система платежей не реализуется до выбора провайдера, нынешний онлайн-AFK не становится офлайн-режимом от замены БД.

## Миграция и проверка

1. Вынести текущее хранилище за интерфейс, сохранив поведение, затем добавить SQL-миграции и PostgreSQL-реализацию. Изолированные тесты используют отдельную настоящую PostgreSQL, не обычные герои.
2. Сделать проверяемый импорт V3: сухой прогон, версия импорта, резервная копия, проверка схемы, дубликатов ID, принадлежности и шести слотов. Сохранить героев, классы, XP/золото, все экземпляры/rolls, pendingItems, экипировку, квесты и действующие ключи доступа. Повтор импорта не дублирует данные.
3. Сравнить данные до/после, протестировать повторные/параллельные команды, отказ до/после commit, восстановление подключения/процесса и резервной копии. Проверить, что старый асинхронный snapshot не откатывает новую продажу/выдачу.
4. При переходе остановить приём мутаций на время окончательного снимка и импорта; один основной писатель, без бесконтрольной двойной записи JSON/SQL. После новых записей в PostgreSQL откат к старому JSON теряет прогресс, поэтому план отката должен учитывать новые операции.
5. Подготовить отдельный релиз и проверку восстановления; production переключать в рамках команды пользователя на выкладку. Исходный файл героев оставлять архивом, локальные герои не заменяют серверных.

## Размещение и пределы

Первый вариант — отдельный PostgreSQL-сервис с постоянным volume и закрытым доступом от игрового сервиса, небольшой пул соединений, резервные копии вне этого сервера и проверка восстановления. Для размещения на текущем Hetzner сначала измерить свободные RAM/CPU/диск: там работают другие сайты. Указанные в DEPLOYMENT.md 256 MiB / 0,5 CPU относятся к прежнему контейнеру игры, а не доказанному бюджету новой базы. Живая инфраструктура в этом исследовании не проверялась. Отдельный VPS/managed-сервис выбирать по фактической нагрузке и требованиям восстановления, не покупать заранее.

PostgreSQL не устраняет просадки FPS от моделей, теней или клиентских анимаций. Вместимость БД/игрового сервера измерять отдельно от клиентского кадра. Горизонтальное масштабирование мира также требует разделения зон/владения симуляцией, оно не появляется автоматически после миграции.

# PostgreSQL-хранилище героев

15 сентября 2026. Локальная реализация для новой, пустой базы PostgreSQL 14+. Импорт прежнего JSON V3 не выполняется. Production не переключён этой задачей.

`openHeroStore({connectionString,writer:true})` создаёт таблицу `schema_migrations`, применяет версию 1 транзакционно и берёт эксклюзивную сессионную advisory-блокировку мира `(8675309,4732)`. Все сохранения писателя проходят через то же удерживаемое соединение; другой процесс с `writer:true` не откроется. При потере соединения или блокировки `health()` возвращает `false`, `commit()` прекращает записи с `StoreUnavailableError`; объект хранилища не переподключается автоматически. `writer:false` предназначен для изолированных тестов или обслуживания базы без игрового процесса и не должен одновременно менять активный мир.

`load(token)` ищет только SHA-256 хеш гостевого ключа и возвращает `{hero,revision}` либо `null`. Ключ в исходном виде не попадает в таблицы и экономический журнал. `commit(entries,operationId,reason?)` выполняет пакет в одной транзакции: ревизия `0` создаёт героя с ревизией `1`, последующее сохранение требует точной ожидаемой ревизии и повышает её на единицу. Повтор с тем же `operationId` и одинаковым содержимым возвращает сохранённые квитанции до проверки ревизий; повтор с другим содержимым даёт `StoreConflictError`. Так можно безопасно повторить запись, если ответ о commit потерялся.

`heroes` содержит скалярный прогресс, класс, положение, HP/MP, ручные статы, квест и ревизию. Небольшие данные текущего удара и откатов навыков находятся в JSONB; полный герой и инвентарь в JSONB не сохраняются. `item_identity` навсегда резервирует ID и отпечаток каждого предмета, даже после продажи. `item_instances` хранит владельца и неизменяемые основные поля; `item_rolls` хранит каждое значение и исходные границы отдельно. `inventory_locations` связывает экземпляр с рюкзаком, экипированным слотом или очередью добычи. Составной FK проверяет владельца, частичные уникальные индексы ограничивают одну вещь в каждой ячейке и слоте. SQL-ограничения отклоняют отрицательные балансы, некорректные диапазоны и недопустимые позиции.

`operation_journal` хранит хеш полезной нагрузки, квитанции, причину, изменение золота и ID добавленных/удалённых вещей. Операция не видна без успешного commit. Предметы с существующими ID нельзя перебросить или создать заново после продажи; смена расположения не меняет броски. Удаление экземпляра допускается для продажи, а изменение основных полей и значений бросков блокируется триггерами.

Проверка реальной базы: `GAME_TEST_DATABASE_URL` указывает на отдельную административную PostgreSQL, где тест создаёт и удаляет временные базы `ashen_test_*`. Без этой переменной тест хранилища пропускается. Обычные `data/` и production-база в этой проверке не используются. Смена схемы в будущем добавляется следующей пронумерованной транзакционной миграцией; уже применённая версия 1 не редактируется после выпуска.
